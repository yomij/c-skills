# Generate Image

## Overview

Generate or edit a bitmap image from the user's request with the bundled script. Use `gpt-5.5` as the main `/responses` model and `gpt-image-2` inside the `image_generation` tool for text-to-image. When the user provides local image input, use the script's `/images/edits` mode with `gpt-image-2`. The skill owns the creative workflow: clarify vague intent, improve the prompt like a professional designer, run the script, then show the result when the current client can render local images. The current stateful continuation handle `previous_response_id` is not supported; use a local `saved_to` image path with `--image` for real follow-up edits.

## Workflow

1. Decide whether the request is specific enough to generate a useful image.
   - Generate directly when the request has a clear subject and usable intent.
   - If the user asks to revise "this image", "the previous image", or another image just generated by this script, use the prior `saved_to` path with `--image` when that file is available.
   - If no local source image is available, generate a new variant from the prior prompt plus the requested changes only if approximate continuity is acceptable.
   - Ask a concise clarifying question when the subject, usage, style, composition, aspect ratio, exact text, or hard constraints are missing or contradictory.
   - If the user provides a local image path, uploaded image path, or reference image path, treat it as existing-image editing or reference-image transformation and pass it with `--image`. Repeat `--image` for multiple references. Use `--mask` for local mask-based edits.
2. After clarification, rewrite the request into an optimized prompt before generation or editing.
   - Follow the Prompt Engineering Directives below; add designer-level details for composition, visual hierarchy, color palette, lighting, material/medium, mood, camera or illustration style, aspect ratio, and negative constraints.
   - Use the Prompt Spec Scaffold below for non-trivial assets so intent, use case, visual decisions, text, and avoid-list stay explicit.
   - Choose the image shape from the current use case, such as square for icons/avatars, portrait for posters or mobile wallpapers, landscape for banners or hero images, and ask if the intended format is unclear.
   - Pass `--size` only for the current request when the desired output shape is clear. Do not store `size` in `config.json`.
   - Keep `gpt-5.5` as the orchestration model and `gpt-image-2` as the rendering model unless the user explicitly needs something else.
   - Preserve user-specified text exactly. Do not invent logos, claims, people, or brands unless the user asked for them.
   - When visible text is requested, put the exact wording in `Text (verbatim)` and let the image model render it directly in the image by default, including UI copy, headlines, Chinese text, and multilingual text.
   - Do not wait for a second approval after optimizing unless the user explicitly asks to review the prompt first.
3. Use the installed skill script at `<installed-skill-root>/scripts/generate_image.py`, and run it from the user's current workspace so relative output directories resolve where the user expects.
   - Codex global default: `${CODEX_HOME:-$HOME/.codex}/skills/generate-image/scripts/generate_image.py`
   - Claude Code global default: `$HOME/.claude/skills/generate-image/scripts/generate_image.py`
   - Project installs: `./.codex/skills/generate-image/scripts/generate_image.py` or `./.claude/skills/generate-image/scripts/generate_image.py`
4. Stream by default for text-to-image. Use streaming so the run can surface `partial_images` previews and the caller can observe progress while `gpt-image-2` renders. Existing-image edits run synchronously through `/images/edits`; do not request `partial_images` with `--image`.
5. Image generation can take a while. Let the command keep running, wait longer before treating it as stuck, and do not kill the process too early.
6. If the prompt is long or shell-sensitive, put it in a temporary prompt file and pass `--prompt-file`.
7. Use `--tool-choice image_generation` for text-to-image when the caller is a fixed "generate image" action and should not decide between multiple tools.
8. Return the generated image. If the current platform can render local images, use the absolute-path Markdown image from the script output. If it cannot, output the full absolute path.

## Asset Workflow Discipline

Borrow the production discipline from the system `imagegen` skill, but stay within this skill's bundled script.

- Decide whether the asset is preview-only or project-bound before generating.
- For project-bound assets, honor the user's requested destination. If no destination is named, keep the output in the current workspace's configured `output_dir` and report the final absolute path.
- Do not overwrite an existing asset unless the user explicitly asked for replacement. Create a clear sibling filename or variant path instead.
- For multiple distinct assets, run one distinct prompt per asset. Do not rely on one vague prompt to produce unrelated deliverables.
- If the image is meant to be consumed by code or documentation, make sure the final asset path is the path the project will reference, not an incidental temporary location.
- Use raster generation only when a bitmap is the right artifact. If the user needs an existing SVG/logo system, deterministic diagram, or simple code-native UI graphic, edit the native source instead of creating a generated bitmap.
- Report the final saved path, the final prompt or prompt set, and any explicit post-processing such as transparent-background processing.

## Follow-Up Image Changes

The current configured `/responses` compatibility path does not support `previous_response_id` for image continuation. Do not use `--previous-response-id`; it is not a reliable edit handle for this skill. Use the local image file path from `saved_to` with `--image` when exact follow-up editing matters.

- For a follow-up request with a prior local output, pass that `saved_to` path as `--image` and describe the desired change in the prompt.
- For a follow-up request without a local image input, generate a new variant from text by combining the prior prompt or `revised_prompt` with the user's requested change.
- Be explicit about uncertainty when regenerating from text only: prompt-only regeneration may preserve style and broad composition, but it cannot guarantee exact identity, pose, layout, or pixel-level continuity.
- The `saved_to` path is the rendered file on disk and can be reused as an edit input with `--image`.
- The `response_id` is useful for tracing the API response, not for multi-round image editing in this workflow.
- Keep each result as a new variant unless the user explicitly asks to replace an existing asset.
- If local-image editing, reference-image transformation, inpainting, or mask-based edits are required, use `--image` and optional `--mask` instead of prompt-only regeneration.

## Prompt Engineering Directives

Rewrite the user's request like an art director, not like a keyword stack. Preserve the user's actual intent, but translate vague requests into concrete visual decisions before calling the image tool.

### Prompt Spec Scaffold

For anything more complex than a quick sketch, write the optimized prompt as a compact production spec. Use only the fields that help:

```text
Use case: <photo/editorial, product mockup, icon/avatar, poster/ad, UI mock, infographic, illustration, concept art, texture/sprite, wallpaper>
Asset type: <where this image will be used>
Primary request: <user's main ask>
Scene/backdrop: <environment>
Subject: <primary subject and action>
Style/medium: <photo, 3D, vector, gouache, etc.>
Composition/framing: <shape, crop, viewpoint, visual hierarchy>
Lighting/mood: <light source, contrast, atmosphere>
Color palette: <dominant and accent colors>
Materials/textures: <surface details>
Text (verbatim): "<exact text, if any>"
Constraints: <must keep or must include>
Avoid: <negative constraints>
```

- If the user's prompt is already specific, preserve it and only normalize it into the scaffold.
- If the user's prompt is generic, add tasteful details only when they materially improve the result.
- Do not add extra characters, brands, slogans, palettes, narrative beats, or side-specific placement unless the request implies them.

### Prompt Blueprint

Build prompts from the visual center outward so the model weights the right thing first:

```text
[core subject and action] + [subject details/materials] + [environment/background] + [lighting design] + [viewpoint/camera language] + [art style/rendering method] + [negative constraints]
```

- Put the primary subject, action, and required count first.
- Put supporting background details after the subject, and keep them subordinate.
- Use concise comma-separated clauses. Avoid long adjective piles that blur the visual priority.
- Specify the output shape when it affects composition, such as square icon, portrait poster, landscape banner, or mobile wallpaper.

### Visualize Abstract Intent

Do not pass abstract mood words alone. Convert them into visible choices:

- "sad": cool color temperature, low contrast, rain or overcast sky, sparse composition, soft shadow falloff, subtle vignette.
- "premium" or "高级感": restrained palette, generous negative space, simple geometry, soft studio lighting, precise material finish, Morandi or muted neutral accents.
- "futuristic" or "科技感": clean industrial surfaces, glass or brushed metal, controlled cyan/white accent light, modular geometry, crisp reflections, minimal clutter.
- "warm" or "治愈": low golden key light, tactile fabrics or wood, rounded forms, gentle color contrast, calm domestic spacing.

Use these as translations, not mandatory recipes. Adapt them to the subject and avoid cliches when the user provides a stronger direction.

### Medium and Camera Cohesion

Choose one coherent visual lane unless the user explicitly requests mixed media. Match the vocabulary to that lane:

- **Photographic / realistic**: include lens and framing terms such as macro lens, 35mm, wide angle, close-up, shallow depth of field, bokeh, Rembrandt lighting, softbox, cinematic rim light, natural window light.
- **3D / product render**: include rendering and material terms such as Octane render, ray tracing, global illumination, matte plastic, brushed aluminum, translucent glass, claymation, subsurface scattering, soft contact shadows.
- **2D illustration / poster**: include illustration terms such as crisp vector, risograph grain, halftone, gouache texture, impasto, ink wash, clean editorial layout, limited color palette.

Do not mix incompatible surface cues casually, such as oil-paint impasto inside a photorealistic product render, unless that contrast is the concept.

### Multi-Subject Spatial Control

When the user asks for two or more subjects or interacting objects:

- Name each subject explicitly every time; avoid ambiguous pronouns.
- Assign clear spatial positions, such as left foreground, right midground, background, seated across a table, or viewed from above.
- Give each subject distinct visual identifiers, such as color, scale, clothing, material, silhouette, or species-specific features.
- Keep interaction mechanics concrete: "the orange cat on the left moves a white chess piece; the black dog on the right watches the board" is better than "they play chess."

### Negative Constraints

Use negative constraints to protect image quality, but never ban something the user asked to include.

- The installed `generate_image.py` script does not expose a separate `--negative-prompt` flag. Add constraints at the end of the optimized prompt as `Negative constraints: ...`.
- If a future interface supports a dedicated negative prompt, pass the constraints there instead of mixing them into the main prompt.
- Default quality floor: `deformed, bad anatomy, blurry, cropped, worst quality, watermark`. Add `text` only when the user did not request visible text or typography.
- For people or character-focused images, add: `extra digits, bad hands, distorted face, asymmetrical eyes`.
- For product, logo, or UI-adjacent images, add constraints against warped geometry, fake UI text, misspelled labels, and unintended logos.

## Transparent Background Requests

Treat transparent-background requests as a deliberate post-processing workflow, not as a casual `background` switch.

- With this `gpt-image-2` script path, prefer a flat chroma-key source image plus local background removal. Do not rely on native `--background transparent` unless model support has been verified.
- Prompt the source image with a uniform key color that is unlikely to appear in the subject, usually `#00ff00` or `#ff00ff`: flat solid chroma-key background, no shadows, no gradients, no texture, no reflections, no floor plane, crisp subject edges, generous padding, and no key color inside the subject.
- After generation, run the installed helper when alpha output is required:

```bash
python3 <installed-skill-root>/scripts/remove_chroma_key.py \
  --input <source.png> \
  --out <final.png> \
  --auto-key border \
  --soft-matte \
  --transparent-threshold 12 \
  --opaque-threshold 220 \
  --despill
```

- Validate transparent outputs before delivery: alpha channel exists, corners are transparent, subject coverage is plausible, and there is no obvious key-color fringe.
- If the subject has hair, fur, glass, smoke, liquids, reflections, soft shadows, or colors that conflict with practical key colors, explain the limitation and ask before switching to another image workflow or model.

```bash
python3 <installed-skill-root>/scripts/generate_image.py --prompt "Keep the same composition, make the lighting brighter, add subtle interface panels, no text, no logos, no watermark" --image /absolute/path/source.png --size 1024x1024 --quality high
```

```bash
python3 <installed-skill-root>/scripts/generate_image.py --prompt "Create a new portrait using the first image for identity and the second image for lighting and color reference, no text, no logos, no watermark" --image /absolute/path/identity.png --image /absolute/path/lighting.png --size 1024x1024 --quality high
```

```bash
python3 <installed-skill-root>/scripts/generate_image.py --prompt "Replace only the masked area with a clean brushed metal panel while preserving the rest of the image" --image /absolute/path/source.png --mask /absolute/path/mask.png --size 1024x1024
```

Run `--help` for the full flag list. Streaming is enabled by default; use `--no-stream` only when a single final payload is preferable. Do not use `.env` or `--env-file`; this skill is configured through `config.json`.

Recommended config:

```json
{
  "api_key": "your-key",
  "base_url": "https://api.xairouter.com/v1",
  "response_model": "gpt-5.5",
  "image_model": "gpt-image-2",
  "output_dir": "data/generated",
  "output_format": "png",
  "quality": "high",
  "background": "opaque"
}
```

Only `api_key` is required. The script defaults to `base_url=https://api.xairouter.com/v1`, `response_model=gpt-5.5`, `image_model=gpt-image-2`, `output_format=png`, and `output_dir=data/generated`. The legacy `model` key is still accepted as an alias for `image_model`. Do not configure `size`; choose it per request and pass `--size` only when useful.

Path resolution priority:

- `--config`
- `GENERATE_IMAGE_CONFIG`
- `GENERATE_IMAGE_HOME/config.json`
- inferred host root from the installed skill path

High-value optional fields:

- `output_format`: use `png` by default; switch to `webp` or `jpeg` only when smaller files matter more than lossless output.
- `output_compression`: use only with `webp` or `jpeg`.
- `partial_images`: ask for streamed preview frames in text-to-image mode when the caller can benefit from progress updates.
- `tool_choice`: set to `image_generation` for deterministic text-to-image flows; leave it automatic otherwise.
- `stream`: leave enabled for text-to-image unless a non-streaming integration requires otherwise.

Do not configure `image`, `mask`, or `size`; choose them per request. `--image` automatically switches the script to `/images/edits`, and `--mask` requires at least one `--image`.

Use `opaque` when you are unsure. A transparent background can be useful, but transparent background requests require the chroma-key workflow above and should be treated as a deliberate choice, not the default.

Restrict config permissions after creating or editing it:

```bash
chmod 600 <config-path>
```

## Response Format

The script prints JSON. Use its `mode`, `markdown`, `saved_to`, and optional `revised_prompt` fields to compose the final reply. Text-to-image mode may include `response_id`; do not present `response_id` as a supported image-edit continuation handle. Edit mode includes `image_inputs` and optional `mask`.

When streaming with `partial_images`, the script may also return `partial_saved_to`.

If images render:

```md
![Generated image](/absolute/path/to/image.png)

mode=generate
saved_to=/absolute/path/to/image.png
response_id=resp_...
revised_prompt=Optional prompt returned by the image generation tool.
```

If images do not render:

```text
mode=generate
saved_to=/absolute/path/to/image.png
response_id=resp_...
revised_prompt=Optional prompt returned by the image generation tool.
```

For edits:

```text
mode=edit
saved_to=/absolute/path/to/edited.png
image_inputs=/absolute/path/to/source.png
mask=/absolute/path/to/mask.png
revised_prompt=Optional prompt returned by the image editing endpoint.
```

## Common Mistakes

- Do not skip clarification when the image would depend on an unknown subject, style, exact text, or aspect ratio.
- Do not ask for confirmation after prompt optimization by default; optimize, generate, and show the result.
- Do not put `size` in `config.json`; a fixed size makes every image share the same shape regardless of its actual purpose.
- Do not move `gpt-image-2` to the top-level responses `model`; keep it inside the `image_generation` tool and let `gpt-5.5` orchestrate the call.
- Do not bypass the installed `generate_image.py`; it follows the required `/responses` + `image_generation` and `/images/edits` logic.
- Do not disable stream by default for text-to-image; the current best path is to stream and request `partial_images` only when previews are useful.
- Do not request `partial_images` with `--image`; edits are synchronous in this script.
- Do not weaken requested visible text into a placeholder or layout note by default. Keep requested typography in the prompt and let the model render it directly in the image by default.
- Do not ask for a transparent background by reflex; treat transparent background as an explicit request with chroma-key or model-support tradeoffs.
- Do not leave a project-bound asset only in an incidental or temporary location; return the final path that the project should reference.
- Do not use `--previous-response-id` for image continuation on the current API path; pass the previous local `saved_to` file as `--image`.
- Do not confuse `response_id` with editable image state.
- Do not kill the process too early just because image generation is slower than a short text response.
- Do not rely on `.env`, environment variables, or another built-in image generation path for this skill.
- Do not claim success unless the script exits successfully and `saved_to` exists.
- Do not paste base64 into the response.
