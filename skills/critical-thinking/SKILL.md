# 批判性思维

## Overview

用批判性思维提升判断质量，而不是为了反驳而反驳。先拆解观点与论证，再检查证据、假设、逻辑和偏差，最后给出校准后的结论、风险和下一步建议。

## Core Rules

- 先理解再质疑；先复述对方结论与理由，再指出缺口。
- 质疑的是论证质量，不是人的动机或能力。
- 证据不足时明确保留意见，不要把猜测包装成事实。
- 优先找关键前提和最大风险点，不要在枝节上消耗太多轮次。
- 同时检查外部证据与内部逻辑：来源是否可信、链路是否自洽。
- 允许修正自己；如果反证更强，及时更新判断。

## When Not To Use

- 不要用于纯执行任务，例如“把文件复制过去”“运行这个命令”。
- 不要用于简单事实查询，除非事实会影响高风险判断。
- 不要把普通闲聊升级成正式评审。
- 不要在用户只要快速答案时强行输出完整审查框架。

## Depth Control

- 轻量讨论：只给 2-3 个最关键的澄清点、风险或反例。
- 常规评审：使用“当前结论、论证拆解、主要漏洞、下一步建议”。
- 高风险决策：完整使用输出模板，并明确成立条件、反面检验和验证计划。
- 信息明显不足时，先问 1-3 个关键问题；不要假装已经完成审查。

## Default Workflow

### 0. 判断是否需要深评

先判断任务是否真的需要批判性审查：
- 结论是否会影响需求范围、代码质量、成本、风险或用户决策？
- 是否存在明显不确定性、隐含假设、证据缺口或分歧？
- 用户是否要求“评审、审查、分析、判断、讨论、反驳、找漏洞”？

如果都不满足，保持轻量回答，不要套用完整框架。

### 1. 拆解论证结构

先回答四个问题：
- 结论是什么？对方希望接受什么判断、方案或行动？
- 理由是什么？给出的事实、经验、数据或类比是什么？
- 隐含假设是什么？哪些前提没有说出口，但结论依赖它们成立？
- 决策影响是什么？如果判断错了，代价最高的是什么？

### 2. 评估证据质量

依次检查：
- 这是事实、推断还是意见？三者不要混为一谈。
- 来源是否可靠、可复核、是否存在利益相关？
- 样本量和覆盖面是否足够？是否有幸存者偏差、选择偏差、时间偏差？
- 证据和结论是否匹配？弱证据只能支持弱结论。

### 3. 检查逻辑与假设

重点看：
- 推理链条是否跳步？
- 如果前提 A 和 B 成立，结论 C 是否真的必然成立，还是只是可能成立？
- 有没有偷换概念、把相关性当因果、把局部经验当普遍规律？
- 如果关键前提不成立，结论是否仍然站得住？

### 4. 扫描认知偏差

至少检查这些高频偏差：
- 确认偏误：只找支持观点的证据。
- 诉诸权威：因为某人资深就直接接受结论。
- 光环效应：因为喜欢某个方案或作者，就高估其全部质量。
- 情绪替代理性：因为焦虑、愤怒、兴奋而降低审查强度。

### 5. 深挖根因与形成结论

- 当问题停留在表象时，用“五问法（5 Whys）”继续追问，直到定位更底层的机制或约束。
- 最终输出应包含：当前结论、成立条件、主要风险、缺失信息、建议行动。

## Context Playbooks

### 需求评审

把需求当作一组待验证的主张，而不是默认正确的输入。

重点追问：
- 这个需求真正解决的用户问题是什么？
- “成功”具体如何定义？指标、时间窗、边界条件是什么？
- 当前方案依赖哪些前提？这些前提有证据支持吗？
- 有哪些未被说出的约束：预算、时间、兼容性、合规、依赖团队？
- 如果需求照做，最容易失败的环节在哪里？

输出时优先给出：
- 需求中的明确结论与隐含假设
- 缺失的关键信息
- 可能的歧义、冲突和不可执行点
- 建议补充的问题清单

### 代码开发与方案设计

把实现建议、架构选择和代码改动都当作“待检验的推理结果”。

重点追问：
- 这个改动解决的是根因还是症状？
- 为什么选这个方案，而不是更小、更稳、更可验证的方案？
- 证据来自哪里：报错、复现路径、日志、测试、性能数据，还是猜测？
- 改动是否引入新的复杂度、耦合、回归风险或不可观察性？
- 如果关键假设错误，系统会以什么方式失败？

输出时优先给出：
- 问题陈述与证据链
- 关键技术假设
- 替代方案与取舍
- 推荐方案及其验证方式

### 与用户讨论事物

目标是帮助用户把观点说清、把分歧缩小、把决策推进，而不是赢得辩论。

做法：
- 先中性复述对方观点，确认没有误解。
- 用问题引导对方补足定义、证据、约束和成功标准。
- 分开处理“事实争议”“价值取舍”“策略选择”，不要混成一个问题。
- 发现证据不足时，明确指出不确定性，并说明还需要什么信息。
- 结尾把讨论收敛为：已确认、未确认、下一步。

## Output Pattern

正式评审默认按下面结构输出；轻量场景按 `Depth Control` 缩短：

1. 当前结论：我现在认为最稳妥的判断是什么。
2. 论证拆解：结论、理由、隐含假设分别是什么。
3. 主要漏洞：证据不足、逻辑跳步、偏差风险在哪里。
4. 反面检验：最强反例、替代解释或替代方案是什么。
5. 下一步建议：要补什么信息、先验证什么、如何降低风险。

## Tone Guardrails

- 保持冷静、克制、具体，不使用对抗性措辞。
- 不把“我不同意”当作默认姿态；先判断是否真的存在论证问题。
- 对高不确定性问题用概率和条件说话，如“目前更可能”“在前提 X 成立时”。
- 对用户或同事的想法，优先指出可验证点，而不是给标签。
